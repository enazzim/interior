# [DB 명세서] 하이브리드 인테리어 관리 시스템: 테이블 설계 의도 및 필드 가이드

본 문서는 인테리어 관리 시스템의 핵심 데이터베이스(총 11개 테이블)의 **설계 의도**와 실무 현장에서 각 **필드가 어떻게 활용되는지**를 상세히 설명한 가이드북입니다.

---

## 1. 조직 및 계정 관리 영역

### 1.1. Companies (회사 테이블)
- **설계 의도**: 이 시스템은 다수의 인테리어 업체가 클라우드에서 각자의 데이터를 관리하는 SaaS(멀티 테넌트) 구조입니다. 따라서 가장 최상위에 업체 자체를 식별하고 청구/구독을 관리하는 테이블이 필요합니다.
- **필드 사용 목적**:
  - `company_id` (PK): 시스템이 A회사와 B회사를 구분하는 절대 기준점.
  - `company_name`: 회사의 상호명.
  - `representative_name`, `business_number`, `address`, `contact_number`: 견적서 출력 시 상단에 고정으로 인쇄되는 '공급자(사업자) 정보'. 매번 입력할 필요 없이 한 번만 세팅하면 됩니다.
  - `subscription_plan`: 해당 업체가 Lite(기본형)인지 Premium(고급형)인지 판단하여, 클라우드 사진 용량이나 계정 추가 개수를 제어합니다.

### 1.2. Users (사용자/직원 테이블)
- **설계 의도**: 한 회사 내에서도 사장님과 직원의 권한(원가 노출 여부 등)을 분리하기 위해, 업체가 아닌 '개인 로그인 계정'을 관리합니다.
- **필드 사용 목적**:
  - `user_id` (PK): 개별 사용자의 로그인 고유 ID.
  - `company_id` (FK): "이 직원은 어느 회사 소속인가?"를 나타내며, 로그인 시 해당 회사의 현장 정보만 볼 수 있게 연결해 줍니다.
  - `email`, `password`: 실제 로그인에 사용되는 보안 인증 정보.
  - `role`: 시스템 권한 제어의 핵심. `ADMIN`이면 마진율과 원가를 볼 수 있고, `STAFF`이면 볼 수 없도록 화면을 차단하는 기준표입니다.

## 2. 현장 관리 영역

### 2.1. Projects (현장/프로젝트 테이블)
- **설계 의도**: 수주한 개별 공사 현장(예: 서초 래미안 리모델링) 단위로 견적서와 사진을 모아두는 '큰 서류철' 역할을 합니다.
- **필드 사용 목적**:
  - `project_id` (PK): 현장 고유 ID.
  - `company_id` (FK): 해당 현장을 소유한 회사.
  - `project_name`, `address`: 현장 화면 상단에 표시될 식별 이름과 실제 주소.
  - `status`: 현재 현장이 '견적 중'인지 '공사 중'인지 '정산 완료'인지를 나타내어 경영 대시보드에서 매출 흐름을 보여주는 기준이 됩니다.
  - `start_date`, `end_date`: 공사 일정을 캘린더 화면에 띄워주기 위해 사용합니다.

### 2.2. Project_Photos (현장 사진 테이블)
- **설계 의도**: 여러 현장에서 직원들이 스마트폰으로 찍어 올리는 비포/애프터 사진이 덮어씌워지는 대참사를 막기 위해, 원본 이름과 시스템 이름을 분리하여 관리합니다.
- **필드 사용 목적**:
  - `photo_id` (PK): 사진 고유 ID.
  - `project_id`, `process_id` (FK): "이 사진은 A현장의 '목공' 사진이다"라고 꼬리표를 달아, 나중에 목공 사진만 필터링해서 볼 수 있게 합니다.
  - `original_file_name`: 사용자가 처음 올렸을 때의 이름(`IMG_0001.jpg`). 나중에 다운받을 때 익숙한 이름으로 돌려주기 위해 기록합니다.
  - `stored_file_name`: 클라우드에 실제 저장되는 '절대 중복되지 않는 이름(UUID)'. 다른 사람의 사진에 덮어씌워지는 것을 원천 차단합니다.
  - `image_url`: 화면에서 사진을 불러와서 보여줄 때 사용하는 웹 주소입니다.

## 3. 자재 및 공정 마스터 영역

### 3.1. Processes (공정 분류 테이블)
- **설계 의도**: 수많은 자재와 견적 내역을 뒤죽박죽 섞이지 않게 서랍(공정)에 담아 분류하고, 견적서 출력 시 실제 공사 순서대로 인쇄하기 위한 척추 역할입니다.
- **필드 사용 목적**:
  - `process_id` (PK), `process_name`: 화면에 '[철거]', '[목공]' 등의 탭을 만들어 자재를 분류할 때 씁니다.
  - `sort_order`: 현장의 실제 공사 흐름(예: 철거=1, 설비=2)을 저장해 두어, 사장님이 무작위로 견적을 입력해도 출력할 때는 알아서 공사 순서대로 예쁘게 정렬되도록 만듭니다.

### 3.2. Materials (자재 마스터 테이블) ★ 핵심
- **설계 의도**: 매번 자재 단가를 타이핑하지 않게 해주는 '사전'이자, ㎡ 면적만 넣으면 몇 박스가 필요한지 알아서 환산해 주는 '두뇌'입니다.
- **필드 사용 목적**:
  - `material_id` (PK), `material_name`: 자재 고유 ID와 자재명.
  - `company_id` (FK): 값이 비어있으면(NULL) 모든 업체가 쓰는 공통 자재, 값이 있으면 우리 회사만 쓰는 '수입 자재' 등으로 구분됩니다.
  - `standard_unit`, `distribution_unit`: 기준 단위(㎡)와 유통 단위(박스/롤)를 구별합니다.
  - `conversion_rate`: 1박스가 1.5㎡를 덮는다면 1.5를 저장. 방 넓이(15㎡)를 입력하면 시스템이 `15 ÷ 1.5`를 계산해 즉시 "10박스 필요"를 도출하게 합니다.
  - `purchase_price`, `labor_price`: 실제 사 오는 원가와 기술자에게 주는 품삯. 시스템이 몰래 더해서 사장님께는 총원가를 보여주고, 고객에게는 두 값을 뭉뚱그려(투트랙) '평당 단가'로 출력하게 해줍니다.

## 4. 견적 및 정산 영역

### 4.1. Estimates (견적서 마스터 테이블)
- **설계 의도**: 하나의 공사 현장에서도 고객 변심으로 인해 1차, 2차 견적서가 여러 개 나올 수 있으므로, 견적서 자체의 버전을 관리합니다.
- **필드 사용 목적**:
  - `estimate_id` (PK), `project_id` (FK): "이 현장에서 발행된 견적서"를 묶어줍니다.
  - `client_vendor_id` (FK): "이 견적서를 받는 고객(수금처)이 누구인가?"를 연결합니다. 출력 시 이 고객의 주소와 이름이 '공급받는 자' 칸에 예쁘게 자동 인쇄됩니다.
  - `author_user_id`: "이 견적을 김대리가 짰는지 사장님이 짰는지" 작성자를 기록하여 책임 소재를 명확히 합니다.
  - `version`: 1차 견적, 수정 견적 등 버전을 분리합니다.
  - `is_final`: 고객이 도장 찍은 최종 견적서를 표시하여(TRUE), 추후 이 내역을 바탕으로 실제 정산 대시보드를 구동합니다.
  - `total_amount`: 견적서의 총 합계 금액.

### 4.2. Estimate_Items (견적 상세 내역 테이블)
- **설계 의도**: 견적서 안의 실제 항목(줄 단위 데이터)들입니다. 면적을 입력받아 환산 수량과 원가, 고객 제출가를 기록합니다.
- **필드 사용 목적**:
  - `item_id` (PK), `estimate_id` (FK): 특정 견적서에 속한 한 줄 데이터.
  - `material_id` (FK): 어떤 자재를 썼는지 마스터에서 정보를 끌어옵니다.
  - `input_area`: 사장님이 줄자로 잰 실제 시공 면적(㎡).
  - `calculated_qty`: 환산 공식을 거쳐 나온 발주용 실제 수량(예: 타일 10박스).
  - `material_cost`, `labor_cost`: 실제 매입 원가와 인건비 (사장님 및 ADMIN 전용 열람용).
  - `customer_unit_price`: 인건비와 마진이 포함되어 고객 견적서에 출력되는 최종 단가 (투트랙 로직의 결과물).

## 5. 정산 관리 영역 (신규 추가)

### 5.1. Incomes (수금 내역 테이블)
- **설계 의도**: 견적만 내고 끝나는 것이 아니라, 고객이 돈을 제대로 냈는지(미수금 관리) 파악하기 위해 실제 통장 입금 내역을 기록하는 장부입니다.
- **필드 사용 목적**:
  - `income_id` (PK): 수금 고유 ID.
  - `project_id` (FK): "어느 현장의 돈인가?"를 연결합니다.
  - `amount`: 실제로 통장에 꽂힌 금액. 이 값들을 모두 더해 견적 총액에서 빼면 대시보드에 '받아야 할 남은 돈(미수금)'이 뜹니다.
  - `income_date`: 언제 입금되었는지 기록.
  - `type`: 이 돈이 계약금인지, 중도금인지 구분합니다.

### 5.2. Expenses (지출/매입 내역 테이블)
- **설계 의도**: 예상 원가(견적)와 실제 지출(통장 출금)은 항상 다릅니다. 추가 지출이나 원가 절감 내역을 기록하여 현장이 끝났을 때의 '진짜 마진(순수익)'을 도출하기 위한 필수 장부입니다.
- **필드 사용 목적**:
  - `expense_id` (PK): 지출 고유 ID.
  - `project_id` (FK), `process_id` (FK): "A현장의 목공 작업에 들어간 지출이다"라고 꼬리표를 달아, 나중에 공정별 지출 통계를 낼 수 있습니다.
  - `vendor_id` (FK): 거래처 마스터와 연결되어, "이 돈이 정확히 OO타일 상사로 나갔다"를 명확히 식별합니다. (기존의 불안정한 텍스트 입력을 대체하여 월말 통합 정산을 가능케 함)
  - `amount`: 실제 송금한 액수. 이 테이블의 총합을 총 수금액에서 빼면 '최종 순수익'이 계산됩니다.
  - `expense_date`: 돈이 나간 날짜를 기록합니다.

### 5.3. Vendors (거래처/협력사/고객 마스터 테이블)
- **설계 의도**: 고객(수금처)과 자재상/작업자(지급처)를 모두 관리하는 핵심 회계 장부입니다. 견적서 출력 시 고객 주소를 자동으로 불러오고, 월말에 지급처별 외상 총액을 한방에 합산해 줍니다.
- **필드 사용 목적**:
  - `vendor_id` (PK), `company_id` (FK): 우리 회사가 관리하는 거래처 고유 ID.
  - `vendor_type`: [수금처, 매입처, 외주처]를 구분하여 '받을 돈'과 '줄 돈'이 섞이는 것을 원천 차단합니다.
  - `business_type`: [사업자, 개인]을 구분합니다. 개인이면 사업자번호 대신 연락처나 주민번호를 받도록 화면을 제어합니다.
  - `vendor_name`, `business_number`, `address`: 거래처의 이름과 주소입니다. 이 정보가 견적서 우측 상단 '공급받는 자' 영역에 1초 만에 자동 인쇄됩니다.
  - `contact_person`, `account_info`: 송금 계좌번호와 담당자 연락처 등 실무 결제 편의 정보를 저장합니다.
